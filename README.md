## Prerequisites
Before proceeding, ensure you have the following installed:
1. Node.js
2. Docker - https://docs.docker.com/desktop/install/mac-install/

## Local Setup
Follow these steps to set up the project locally:
1. Clone the repository:
    ```
    git clone <repository-url>
    ```

2. Install dependencies:
    ```
    npm install
    ```

## How to Run the Project
To run the project locally, use the following command:
```

add your google email in insertDataForUIFlow function(scripts/seedData/insertSeedData.ts) file 
under members list to use already seeded data on UI flow, then

run the docker locally
npm run start:local
``` 

To run end-to-end tests, execute:
```
npm run e2etest
```

To format your code using ESLint, run:
```

```

To run performance tests:

## Troubleshoot

- Ensure docker daemon is running
- Run the command `npm run start:local`
  - These docker images will be started locally: db, mailhog and sqs
  - Routes will be generated by the tsoa script
  - Mock Queues will be created on the local sqs instance
  - The seed data will be inserted into db and will be printed on the console logs with the respective id and the value `| Script   | insertSeedData |`
  - The server and the consumer will start using serverless offline
- Copy the generated swagger.yaml (src/server/routes) and import it into Postman
  - The routes, models and examples should now be populated in Postman
  - Suggested to set up environment variables in Postman to address the respective environment
- On shutting down the local instance, all the docker containers along with their volumes will be removed
- [Go here](http://localhost:8025/) to check email locally
- [Go here](http://localhost:9325/) to check messages in the queue locally
- Use this connection string `mongodb://localhost:27018/` to connect to the docker db instance

## Migration

### Steps for migrating schema:-

1. Step 1: Increment the SCHEMA_VERSION field in the repository file for that particular schema. For example if you are updating the organisation schema, then increment the SCHEMA_VERSION field of organisation repository.

2. Step 2: If the schema changes are a breaking change then add the logic for upgrading the older documents to the new schema in the upgrade() function. 

To know about what is a breaking change refer the below documentations:

https://www.mongodb.com/docs/atlas/app-services/sync/data-model/update-schema/
https://www.mongodb.com/docs/atlas/app-services/sync/data-model/migrate-schema-partner-collection/

3. Step 3: After you are done with schema update and done with above changes, you can run the below scripts:- 
For running the migration on local db: `npm run script:run-schema-migration`
For running the migration on staging db: `npm run script:run-schema-migration staging`
For running the migration on production db: `npm run script:run-schema-migration prod`


- NOTE:- All of these scripts have to run manually on your machine as these scripts are not part of the pipeline because a gitlab pipeline job only executes for about 20 - 30 mins and terminates after that, but the migration scripts can take longer than that to migrate all the documents present in db. That is the reason these scripts are not part of the pipeline.

### Types of Upgrade:-

- There are 2 types of upgrade that happen when you do the above changes:-
Through the migration script: When you run the migration command the documents are upgraded in batches. Batch size of every repository is present in the migrate() method of every repository named as limit. 
On request migration: Whenever any document is requested for any read or write, we first check whether this document belongs to an old schema_version. If found, we migrate the document to the new schema.

### Question: Is the second type of migration even needed when we are already batch upgrading the documents through migration script

Ans: Yes. Imagine a scenario that you are running the migration scripts and the batch migrations for organisations are getting performed. Now a batch of organisations is being picked from db for migrating. In the meantime a user requested an organisation and updated the organisation and before the user you performed a batch write operation in db. You stored the upgraded document through script. But after you the user re-write the old schema_version document in db. This will cause inconsistency, that's why a second type of migration was introduced.
